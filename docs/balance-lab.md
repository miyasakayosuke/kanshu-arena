# Balance Lab：開発用の再現可能なバランス検証

Balance Lab は、現行の戦闘処理で「この数値・編成を変えると何が起きるか」を比較する開発専用 CLI です。固定対戦とシード付き合法編成を使い、勝敗だけでなく、行動機会・MP・支援・個体への依存を記録します。

**本番の能力値、特技、ゲーム内 CPU、UI、保存データは変更しません。** 候補設定は検証用のコピーにだけ適用します。自動でバランスを調整したり、候補をゲームへ反映したりするツールではありません。

## 実行方法

リポジトリ直下で Node.js **22.18 以上、または 24** を使います。エンジンの TypeScript を Node の型除去で読み込みます。

```sh
npm ci

# 最小の確認実行
npm run lab -- run --config configs/balance-lab/smoke.json --out lab-results/smoke

# フェンリルの MP 仮説を試す候補例
npm run lab -- run --config configs/balance-lab/fenrir-mp-example.json --out lab-results/fenrir-mp

# 系統追加の固定32シード：開幕の自然障壁10%を無効にする対照
npm run lab -- run --config configs/balance-lab/family-wave.json --out lab-results/family-wave-ward-disabled

# 同じ検証群で自然障壁10%→15%だけを変更する候補
npm run lab -- run --config configs/balance-lab/family-wave-ward15.json --out lab-results/family-wave-ward15

# 最終ソースで初期案の数値を明示的に復元する比較
npm run lab -- run --config configs/balance-lab/family-wave-final-vs-initial.json --out lab-results/family-wave-final-vs-initial

# 明示的に保存した30生成編成＋7対策編成を同じ対象へ当てる広い確認
npm run lab -- run --config configs/balance-lab/family-wave-broad.json --out lab-results/family-wave-final-broad

# シード数・生成編成数を増やす
npm run lab -- run --config configs/balance-lab/fenrir-mp-example.json --out lab-results/fenrir-mp-64 --seeds 64 --sample-teams 16

# 保存した report.json の matches から対象の ID を選び、1戦を再生する
npm run lab -- replay --report lab-results/smoke/report.json --match MATCH_ID --out lab-results/replay.json

# 失敗記録が作られた場合だけ、その同じ戦闘を再実行する
npm run lab -- replay-failure --failure lab-results/smoke/failure.json --out lab-results/repeated-failure.json

# 通常の回帰テストと本番ビルドも別に実行する
npm test
npm run build
```

既存の出力先に `config.json`・`report.json`・`report.md`・`failure.json` がある場合、`run` は上書きを拒否します。出力先を変えるか、意図して再実行する場合だけ `--overwrite` を付けてください。この指定は設定検証に成功してから、その4種類の既存生成ファイルを消して実行します。不正な設定なら古いファイルを保持し、以前の結果であることを警告します。`npm run lab:smoke` は動作確認用の既定フォルダーに限り `--overwrite` を含みます。

`MATCH_ID` は説明用の置き換え文字列です。実際のレポートにある対象試合の ID に置き換えてください。集計を増やす前に smoke 実行と単戦再生が成功することを確認します。出力先を実験ごとに分けると、比較の根拠を残せます。

`smoke.json` は変更なしの candidate を baseline と比較する動作確認用の小標本です。`npm run lab:smoke` でも同じ設定を実行できます。`fenrir-mp-example.json` はフェンリルの最大 MP を 60→65 にする未採用の仮説例です。結果を見て数値を変更した場合は、その設定を新しい実験として保存し、同じ検証群で比較します。

`family-wave.json` と `family-wave-ward15.json` は同じ固定32シード・10編成・25対面に、全10編成のミラーを加えます。両サイドと両候補版を含めて、各設定は **4,480戦** です。生成編成は含めません。前者は現行10%の自然障壁を無効にする機構の対照、後者は10%→15%の感度確認であり、本番値を変更しません。フェンリルの能力・技・群気には変更を加えません。

`family-wave-final-vs-initial.json` は18編成・79対面・18ミラー・32シードの **12,416戦**。baselineは最終値、candidateは初期案の玄武ATK45／全体威力46・障壁20%・ラタトスク連撃威力0を明示的に復元します。`family-wave-broad.json` は39編成・75対面・39ミラー・16シードの **7,296戦**。保存済みの生成30編成を両方の自然編成に必ず当てるため、汎用の `sampling` の対戦先循環には依存しません。candidateは変更なしの対照です。

その他の `family-wave-genbu-*` などは履歴用の候補指定です。実行時の現行版をbaselineとするので、当時の未コミット初期案を再現する設定とは呼びません。[検証記録](./family-wave-balance-audit.md) は過去の探索と最終ソース上の比較を分けています。

検証編成には全獣 `[12,0,2,11,13]`（COST17）、全自然 `[14,3,6,9,10]`（COST15）、従来の混成獣 `[12,0,2,6,10]`（COST15）、先制、毒＋浄化、解除技を持つ編成（COST14）を含めます。核の同コスト置換、玄武をリーダーにしない同5体、自然核なしの2枠置換も対照に置きます。**核の置換は個体・技・系統人数やリーダーも変わり得るため、開幕支援だけの因果比較ではありません。** 解除技を所有していても、自動方策が毎回それを選ぶ保証はありません。実際の `cast` と `break` を確認します。

既存の main 向け CI でも `npm run lab:smoke` を実行し、出力を `balance-lab-smoke` artifact として 7 日間保存します。Lab のレポートは本番配信用の `dist` とは別です。

### CLI の上書きと実行量

- `--seeds N` はシードそのものではなく**シードの個数**です。設定中のシード一覧を、`sampling.seed`（指定がなければ `20261009`）から生成する N 個の決定論的なシードに置き換えます。範囲は 1〜1000。
- `--sample-teams N` は `sampling.count` を置き換えます。範囲は 0〜100。固定シナリオはそのまま残ります。
- 同じシナリオに baseline / candidate と両サイドの試合を含めるため、シード数と生成編成数だけで総試合数は決まりません。実際の予定数はレポートの `scheduleCounts` で確認します。
- 総試合数の上限は 20,000。メモリとレポートサイズを制限するための上限です。上限超過は実行前にエラーとなり、勝手に一部だけ抽出して実行した結果は作りません。同梱設定では既定実行が 736 戦、上の 64 シード・16 生成編成の例は 12,032 戦です。

設定ファイルは JSON のみです。主な項目は次のとおりです。

- `schemaVersion: 1`、`suiteId`：設定形式の版と実験 ID。
- `seeds`：重複なしの 32-bit 非負整数シード一覧。`costLimit`：15 または 17。
- `teams`：`id`、役割を記す `role`、先頭をリーダーとする 5 体の `ids`。
- `scenarios`：`id`、team A の `a`、team B の `b`。必要なら `keyUnitId` と `complaintIds` を付けます。
- `candidate`：`id`、`label`、差分の `overrides`。空の `overrides: {}` は変更なしの対照。
- `sampling`：追加編成数の `count` と、その抽出・枠順用の `seed`。
- `complaints`：後述の、出典と仮説を結び付ける記録。

未知のフィールド、不正な ID、重複個体、コスト超過、未対応の効果は検証でエラーにします。ID の `sample-` / `mirror-` 接頭辞は生成用に予約されているため、自分のシナリオには使わないでください。

### 出力

- `report.md`：人が最初に読む集計。差の方向だけでなく、シナリオごとの条件を確認します。
- `report.json`：設定、方法、予定試合数、集計、各試合の ID と結果を持つ機械可読の記録。
- `config.json`：CLI の上書きを含む、その実験の実行設定。
- `failure.json`：戦闘処理で例外や不変条件違反が起きた場合の、対象試合の要求とトレース。通常のバランス集計の代わりに、失敗の再現・診断に使います。

`report.json` の主な入口は `summary.baseline` / `summary.candidate` / `summary.pairedDelta`、シナリオ別の `scenarios`、単戦の `matches` です。`summary` は通常対戦だけの集計で、ミラーは `mirrorControls` に分けています。`scenarios[].kind` は通常の組み合わせ `matchup` と対照の `mirror` を区別します。単戦には `scenarioId`、`variant`、`orientation`、`seed`、`teamAId`、`teamBId`、`result` が残ります。指標の定義は `methodology.metricDefinitions`、解釈の限界は `methodology.limitations` にも保存します。

## 対戦を揃える仕組み

### 両軍に同じ自動方策

両軍の指示選択に既存の `autoOrders` 方策を使い、ダメージ・MP消費・行動順・状態の期限・勝敗は本番の `advanceWithEvents` で解決します。独自のダメージ式や簡略化した模擬戦闘へ置き換えません。Lab 内の方策統一は、ゲーム内の敵 CPU の変更を意味しません。

両軍のリーダーを有効にして開始し、Lab は `advanceWithEvents` の任意引数 `enemyOrders` に `autoOrders(state, 'enemies')` を渡します。この引数を省略するゲーム本体では従来の敵 CPU を維持します。

[既存のフェンリル監査](./fenrir-balance-audit.md)は、味方が `autoOrders`、敵が既存のシード付き技選択という異なる方策を使っていました。そこで観測された「味方側 96.0%、敵側 6.3%」などの値は、その条件付きの過去の証拠です。今回の結果と同じ母集団の測定値として合算したり、差をそのままバランス改善量と呼んだりしません。

### 合法編成と比較単位

- 固定シナリオで、確認したい対策や組み合わせを明示します。
- シード付きで生成する編成も、必ず 5 体・同一 ID の重複なし・対象ルールの COST17 または COST15 以内にします。
- 先頭のリーダーと枠順も入力条件です。メンバーが同じでも、先頭を変えた編成は同じ条件ではありません。
- baseline と candidate に同じシナリオ・編成・開始シードを与え、両方の物理サイドで対戦させます。
- 同一編成同士のミラーを対照として置き、片側への偏りを別に見ます。

生成編成は、固定編成で既に使っている 5 体の集合を除き、baseline と candidate の双方で合法な集合から選び、先頭と枠順もシード付きで並べ替えます。各生成編成は固定編成の一つと対戦し、全編成にミラーを追加します。全編成同士の総当たりではありません。必要数の合法な未使用集合がなければ、数を黙って減らさずエラーにします。

candidate は**両軍に適用するルール・名簿の候補版**です。対象個体が相手側にもいれば、相手側にも同じ変更が適用されます。注目するチームだけに強化を与える実験ではありません。対象個体が双方にいる試合と、片側にだけいる試合を分けて読むことが重要です。

合法であることと同コストであることは別です。低コスト編成を高コスト編成と比較する場合は、その差を残して解釈してください。生成編成は現行の全編成や実際のプレイヤー使用率を代表する保証がありません。固定シナリオ、生成編成、ミラーの結果を混ぜた総合値だけで判断しないでください。

### 同じシードが保証する範囲

同じエンジン・Lab・入力設定・編成・シード・方策を再実行するための仕組みです。候補によって行動や撃破時点が変わると、乱数の消費回数も変わります。**開始シードが同じでも、baseline と candidate の各行動が同じ乱数を受け取るとは限りません。** 対応のある実験条件として扱い、同じ乱数列位置まで固定した反実仮想とは呼びません。

再現のため、設定だけでなく、使用したコミットと出力レポートも保存してください。結果が変わったときは、数値差を解釈する前にエンジン・Lab・設定の差を確認します。

`report.json` の `source` にはゲーム版、Git コミット、未コミット変更の有無、Node 版、エンジン・Lab・実行設定それぞれの SHA-256 が残ります。未コミット変更がある場合はコミット ID だけで再現できないため、実際のソースを保持してください。

`replay` は元のレポートに埋め込まれた設定を使います。現在のエンジン、Lab、埋め込み設定のハッシュが記録時と異なる場合は再生を拒否し、再生成したトレースの `traceHash` も保存値と照合します。成功時の出力には初期状態、各ターンの指示・イベント・乱数状態・資源のスナップショット、最終状態が入ります。変更後のコードで以前の結果を再現したことにしないための検査です。ハッシュが違う場合は、記録時のソースへ戻して再生するか、変更後のコードで別の実験として再実行してください。

`replay-failure` も同じソース・設定の照合を行い、埋め込み設定から復元した対戦予定、`matchId`、保存された試合要求が一致することを確認します。保存済みトレースの SHA-256 も検証し、再実行した試合要求・エラーメッセージ・失敗トレースの SHA-256 がすべて一致した場合にだけ `reproducedFailure: true` を保存します。戦闘処理自体が例外を投げた場合も、失敗したターンの両軍の指示、開始シード、実行前の状態を `activeAttempt` に残します。

再実行が成功した場合や、要求・エラー・トレースのいずれかが異なった場合は、得られたトレースを保存して異常終了し、元の失敗が再現したとは報告しません。再実行前の照合不一致はその時点で拒否します。設定検証エラーなど、実行できる試合要求を持たないエラーはこの対象外です。

## 変更できるものと、扱わないもの

候補設定は、Lab が検証する能力値、習得特技、リーダー補正、開幕の群気・自然障壁の設定に限定します。まず同梱設定をコピーし、小さな変更から比較してください。設定値の変更と編成の変更を同時に増やすほど、差の理由を切り分けにくくなります。

設定可能な候補フィールドは次の範囲です。JSON の構造は同梱設定を起点にしてください。

- 個体：`hp`、`mp`、`atk`、`speed`、`cost`、`family`、`skills`。`skills` は一部だけの差分ではなく、最大 4 枠の配列全体を指定します。
- リーダー：既存の `stat` / `percent` / `family` と `secondary` の構造に従う補正。
- 開幕群気：`openingRally` の `enabled`、`percent`、`turns`。
- 開幕自然障壁：`openingWard` の `enabled`、`percent`、`turns`。例：`{"openingWard":{"percent":15}}`。いずれの開幕支援も `percent` は0〜100、`turns` は0〜20の整数。省略した値は現行既定値を使います。`enabled:false` はその支援のみを除き、他方の支援やリーダー補正を維持します。

コストを変更する場合も、両方の候補版で編成が合法であることが必要です。`family` は既存の系統分類の範囲で扱い、名前だけ新しい任意特性を増やす用途には使いません。

個体の `family` は `"beast"`、`"nature"` または系統を外す `null`。リーダーの対象系統も獣・自然に対応します。リーダーには `name` と `description` も必要で、主補正は `hp` / `atk` / `speed`、副補正は異なる `atk` / `speed` に限ります。開幕群気の発生元はフェンリル（ID12）、自然障壁の発生元は玄武（ID14）で、いずれもリーダーでなくても同じ軍の対象系統へ付与します。系統の上書きは支援の受け手・リーダー補正・条件付き連撃の判定にも反映します。群気の割合や期間を変更しても、初ターンの行動順に群気の素早さ補正が乗らない既存仕様は変わりません。

自然障壁の現行値は2ターン・直接ダメージ10%軽減です。守りの50%軽減とは重ねず、強い方だけを使い、毒の継続ダメージは軽減しません。通常の防御解除技は着弾前に守り・自然障壁を除き、フェンリルの連撃は各着弾後に守り・群気・自然障壁を除きます。永続リーダー補正は解除しません。`openingWard` 候補は両軍の開始状態へ独立に適用し、玄武がいない軍へ障壁を作りません。

ランダム連撃の `familyBonusHit` は `"beast"` または `"nature"` を受け付けます。`kind:"hit"` と `randomHits` が必要で、全体技や回復などには付けられません。最初の5枠すべてが指定系統ならその技だけ1発増えます。戦闘不能になった味方も元の5枠として数えます。現行ラタトスクの条件連撃は獣5体で3→4発です。

効果は現行エンジンが持つ範囲だけです。

- 能力値は HP・MP・攻撃・素早さ。**防御力・賢さは未実装**です。
- 習得特技は最大 4 枠。無料の通常攻撃と共通防御は別枠です。
- 特技種別は直接攻撃 `hit`、回復 `heal`、自己防御 `guard`、毒 `poison`、単体守護 `protect`、毒解除＋回復 `cleanse`。
- 現行仕様の威力・消費 MP・優先度、対応する全体攻撃・ランダム連撃・系統限定の追加1発・防御解除を扱います。毒・守り・群気・自然障壁・永続リーダー効果の解除可否と処理順は既存エンジンに従います。
- リーダー補正は既存の能力値補正と対象系統の仕組み、開幕支援は既存の群気・自然障壁の仕組みを使います。

任意の JavaScript、独自のスクリプト特性、新しい状態異常、反射、回避、行動不能、蘇生、属性耐性、装備、育成、オンライン戦は追加しません。説明用の名前を設定しても、未実装の効果が生まれるわけではありません。新しい機構を比較するには、まず別途エンジンの設計・実装・テストが必要です。

## 指標の読み方

### 勝敗と所要ターン

勝ち・負け・引き分けは**シナリオで指定した team A** の結果です。物理サイドを入れ替えても注目する team A の同一性を維持します。`winRate` は勝ち数 ÷ 試合数、`drawRate` は引き分け数 ÷ 試合数。`scoreRate` は勝ち 1、引き分け 0.5、負け 0 の平均なので、`winRate` とは異なります。`meanTurns` は完了したターン数の平均です。割合は 0〜1 の値で、例えば差 `0.05` は 5 パーセントポイントです。

`pairedDelta` は、同じシナリオ・シード・向きで対応させた candidate − baseline の差です。`scoreRateChange` はシードごとに対応差を平均して集計します。`approximate95Interval` は、そのシード単位の平均差に対する正規近似区間です。1 シードなら計算せず `null`。固定した検証群内の参考値であり、プレイヤー全体や全編成の真のバランスに対する保証ではありません。

最大 20 ターンに達した試合は、現行仕様どおり両軍の残り HP 割合の合計で判定します。ターン上限での決着を全滅勝ちと混同せず、長期化の件数と併せて読みます。

### 物理サイドの偏りと、先に実行した側

`allies` / `enemies` はエンジン上の物理サイドです。`physicalAllyScoreRate` は物理 `allies` 側の平均スコア、`physicalAllyScoreBias` はその値 − 0.5 です。偏りが正なら `allies` 寄り、負なら `enemies` 寄りです。ミラーの team A スコアは両サイド入れ替えによって 0.5 になるため、その値だけを偏りなしの根拠にせず、ミラーの `physicalAllyScoreRate` を確認してください。

**`allies` 側を「先手」と呼びません。** 実際の行動順は特技優先度・素早さ・同速抽選で決まります。`firstCastSideScoreRate` は、その試合で最初に実際に発動した `cast` イベントの側の平均スコアです。最初の発動が守護や防御なら、それも最初の発動です。先にダメージを与えた側や、先に入力された側とは区別します。先行側のスコアも観測上の関連であり、先行だけが勝因である証明ではありません。

### 各個体の働き

- **直接ダメージ**：`meanDirectDamage`。イベントに残った実 HP 減少量。残り HP を超える過剰ダメージを加算しません。毒の継続ダメージには元の付与者の記録がないため、直接攻撃者の成果として混ぜず、受けた側の `meanPoisonDamageTaken` に分けます。
- **回復**：`meanHealing`。実際に増えた HP。満 HP への空回復や、最大 HP を超える分は加算しません。
- **支援・解除**：`meanGuardApplications`、`meanEffectiveCleanses`、`meanPoisonApplications`、`meanDispelApplications`。守りの付与、実際に毒を消した浄化、毒の付与、守り・群気・自然障壁を消した解除イベントを分けます。守りの重ねがけ・毒の更新も付与として数えるため、新しい保護対象数や予防したダメージとは異なります。開幕の自然障壁は自動付与なので守りの発動回数には含めません。1 回の解除で複数の状態を消しても、解除イベントは 1 回です。自然障壁の残りターンと軽減率は再生・失敗記録のスナップショットにも残りますが、予防ダメージ量として因果的に配分する指標はありません。
- **発動と MP**：`meanCasts` は無料コマンドも含む全発動、`meanSpecialCasts` は習得特技の発動、`meanPaidCasts` は正の MP を消費する発動、`meanMpSpent` は実 MP 消費。選んだ指示だけでは集計せず、手番前に倒れた個体に予定していた MP を課金しません。
- **MP不足の機会**：`meanNoAffordableSpecialTurns`。ターン開始時に生存していて、正の MP を要する習得特技を持つが、その**どれも**所持 MP で使えない個体・ターンの数を合計し、試合数で割ります。ある特技一つが使えないだけでは数えません。無料攻撃が残るため「行動不能」ではなく、有用な特技を選ぶはずだったことの証明でもありません。
- **MPがちょうど 0 の機会**：`meanZeroMpTurns`。生存していて MP0 でターンを始めた個体・ターン数の 1 試合平均。MP が残っていても全有料特技を使えないケースとは区別します。
- **一度も発動せずに倒れた割合**：`zeroCastDeathRate`。発動 0 のまま倒れた team A 個体数 ÷（5 × 試合数）。死亡個体だけを分母にした割合ではありません。通常攻撃・防御・支援も発動に含むため、支援してから倒れた個体は該当しません。

`mean…` は特記がなければ team A の 1 試合あたり平均です。各個体の内訳は `matches[].result.units`、物理サイド別の内訳は `matches[].result.sides` にあります。

ダメージが小さい支援役を、それだけで無価値と判定しないでください。回復・解除・守護と、そのために使った手番や MP を併せて評価します。

### 個体への集中と、置き換え比較

`meanDamageConcentration` は、チームの直接ダメージに占める各個体の割合の最大値を試合ごとに求めた平均です。直接ダメージが 0 の試合は 0 とします。高い値は特定個体への攻撃成果の集中を示しますが、支援の価値、連携、毒、代替不能性まで証明するものではありません。

シナリオに `keyUnitId` を指定すると、その team A 個体について `keyUnit` に初ターン死亡、発動前死亡、生存時・死亡時のチームスコアなどを記録します。生存と勝利の関連は、個体の生存だけが勝因であることを示しません。該当する生存例や死亡例がなければ、その条件付き平均は `null` です。

特定個体への依存を調べる場合は、対象個体を合法な別個体に置き換えたシナリオを用意し、同じ相手・シード・両サイドで比較します。これは「一人減らした 4 対 5」とは異なります。コスト、先頭リーダー、系統支援の適用も変わり得るため、置換した個体だけの純粋な因果効果とは断定しません。

## 不満・仮説をシナリオへ結び付ける

プレイヤーの不満を扱うときは、出典、観測範囲、検証仮説、対象シナリオ、見る指標を残します。出典のない例や推測は **仮説・未検証** のまま扱い、「プレイヤーの総意」「確認済みの問題」と書き換えません。出典があっても、一人の感想や古いバージョンの記録を現行全体へ一般化しません。

記録の基本形は次のとおりです。これは書き方の例であり、実際の苦情の引用や実測結果ではありません。出典未確認なら `status` は `hypothesis`、`source` は `null` にします。実在するリンクを確認するまで仮の URL を入れないでください。この例のシナリオ ID を使う場合は、そのシナリオが設定に存在することを確認します。

```json
{
  "id": "hypothesis-mp-before-impact",
  "status": "hypothesis",
  "source": null,
  "complaint": "MPが重要な局面より前に不足するのではないか",
  "hypothesis": "MP設定を変えると、長期戦での特技利用機会が変わる",
  "scenarioIds": ["beast-vs-guard-heal"],
  "metrics": [
    {
      "name": "meanNoAffordableSpecialTurns",
      "direction": "decrease",
      "rationale": "有料特技を使えない局面が減るか確認する"
    }
  ],
  "limitations": [
    "出典未確認の仮説であり、プレイヤーからの苦情を確認していない",
    "MP増加が人間のプレイ体験を改善するかは、この検証だけでは分からない"
  ]
}
```

実際に記録するときは、次を確認します。

1. 出典が確認できたら `source` を `{ "url": "…", "title": "…", "observedAt": "YYYY-MM-DD", "scope": "…" }` の形で埋め、`status` を `sourced` にする。取得できなかった内容を読んだことにしない。`sourced` は出典があるという意味で、仮説の正しさが確認されたという意味ではない。
2. 苦情と原因の仮説を分ける。「使いづらい」から直ちに「攻撃力不足」と決め付けない。
3. `scenarioIds` を実行設定に存在する ID に結び付ける。
4. `metrics` の `name` は `methodology.metricDefinitions` のキーを使う。`direction` は `increase` / `decrease` / `observe` のいずれかにし、`rationale` に理由を書く。
5. 反対の結果も残す。数値が期待方向へ動いたことと、問題が解決したことを区別する。

## 結果から判断できないこと

- この自動方策は人間の最善手、上級者の対策選択、プレイヤーの使用率を再現しません。
- 平均勝率だけでは、相性の極端さ、特定の対策不在、短期決着、支援役の不在を見落とします。シナリオ別・相手別・個体別の結果と再生ログを確認してください。
- 同じ編成を多数のシードで繰り返しても、独立した多数のプレイヤーを観測したことにはなりません。小標本の差を安定した改善と断定しません。
- 50% に近い勝率やゼロに近いサイド偏りは、楽しさ、公平感、多様性、人間同士の対戦バランスの証明ではありません。
- 固定の勝率閾値で「合格」「不合格」を自動判定せず、本番数値も自動更新しません。

この Lab は、問題を絞って再現し、次に人間が試す条件を選ぶための証拠を作ります。採用判断には実際のプレイテストと、その版での回帰確認が必要です。
